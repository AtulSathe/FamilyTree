🧠 Design Decisions

▼
DecisionReasoning
record types for all DTOs CLAUDE.md coding conventions explicitly require record types for DTOs. Records are immutable and get value-equality for free — ideal for HTTP response/request objects.
PersonDetailResponse is a separate record, not inheriting PersonResponse C# positional records do not support constructor inheritance. A flat record with all fields is cleaner than a workaround with a non-positional base. Both share the same 9 base fields by repetition.
Jobs typed as List<JobDto>, not raw JSON string The domain stores Jobs as a JSON string for EF Core compatibility. The DTO layer deserialises to a typed list so the frontend gets a proper array — the service layer will handle the serialisation boundary.
CustomFields typed as Dictionary<string, object?> The extended_fields/CustomFields columns are arbitrary JSON. A dictionary preserves the open-ended nature while still being serialisable by System.Text.Json.
UpdatePersonRequest excludes TreeId Tree membership is managed separately via POST/DELETE /trees/{treeId}/members/{personId}. Including TreeId in an update would conflate person data with membership data.
RelationDto.Direction field (in | out | both) Gremlin edges are directed. The frontend needs to know directionality to render edges correctly (e.g. parent_of vs child_of visually look different). both is used for spouse/sibling edges that are always bidirectional.
[Required] on request records instead of nullable Non-nullable positional record parameters are already implicitly required for model binding. Adding [Required] makes the validation intent explicit in Swagger and enables automatic 400 responses from the minimal API validation pipeline.
SearchResultDto includes PhotoBlobUrl The plan didn't specify it but FR-11 says search returns a "person card with tree/surname context". The PersonCard component will need the photo to render correctly — adding it here avoids a second round-trip.

⚠️ Assumptions Made

▼
AssumptionRationale / Risk
PersonDetailResponse does not inherit PersonResponse Positional record inheritance is not supported in C#. Low risk — both return the same base fields; services will project them identically.
Jobs deserialised to List<JobDto> in the DTO layer (not raw JSON) Services will call JsonSerializer.Deserialize<List<JobDto>>(person.Detail.Jobs). If the DB value is null the service will return an empty list.
SearchResultDto includes PhotoBlobUrl (not in original plan) FR-11 specifies a "person card" in results. PersonCard component needs the photo. Risk: negligible — only adds one field to the search query join.
Role validation in request DTOs uses string, not an enum The domain stores roles as strings (to match Azure AD B2C JWT claims). Using an enum here would require a custom JSON converter. Services will validate allowed values.
